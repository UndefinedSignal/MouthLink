# MouthLink — кастомный трекинг рта для PICO 4 Pro

Свой трекинг рта для PICO 4 Pro: кадры камеры рта уходят на ПК, там своя модель
считает блендшейпы и отдаёт их в VRChat через VRCFaceTracking. Цель — то, чего
стоковый трекинг не умеет: персональная калибровка под своё лицо и каналы,
которых в стоке нет (язык в стороны, раздельные щёки), при более высокой частоте.

## Зачем

Стоковый рот PICO работает, но ограничен: низкая частота, фиксированный набор
форм, никакой подстройки под конкретное лицо. Шлем свой, рут есть — значит, можно
снять кадры камеры рта самому, обучить модель под себя и получить выразительность,
которой у стока нет. Глаза при этом остаются на стоке (там всё хорошо: 90 Гц,
реальные зрачки, калибровка взгляда), а своим делаем только рот.

## Как устроено

```
   ШЛЕМ (PICO 4 Pro)                          ПК
 ┌────────────────────┐            ┌──────────────────────────────┐
 │ камера рта          │            │ MouthLink.Receiver           │
 │   │                 │            │   приём, сборка кадров,      │
 │   ▼                 │  UDP       │   запись .mlrec, просмотр    │
 │ захват кадра ──────────────────▶ │        │                     │
 │ (ТВОЯ часть)        │  протокол  │        ▼                     │
 │                     │  MouthLink │   модель (ONNX) ──▶ VRCFT ──▶ VRChat (рот)
 └────────────────────┘            │                              │
                                   │ глаза: сток PicoET→бридж→UPM ─▶ VRChat (глаза)
                                   └──────────────────────────────┘
```

Поток разбит на две независимые части:

- **Сторона шлема — захват кадра камеры рта и отправка по сети.** Это пишешь ты
  (сам или с автором PicoET). См. «Граница» ниже.
- **Сторона ПК — всё остальное.** Приём, сборка, запись, просмотр, обучение
  модели, отдача в VRChat. Это содержимое репозитория, собрано и проверено.

Глаза не трогаем: они идут штатным путём PicoET → PicoFacialBridge → UnifiedPicoModule
с `DisableFaceTracking`, а свой модуль VRCFT отвечает только за рот.

## Что уже готово (сторона ПК)

| Компонент | Что делает | Статус |
|-----------|-----------|--------|
| `PROTOCOL.md` | протокол шлем→ПК: UDP, фрагментация кадра, подписка, синхронизация часов | спека |
| `MouthLink.Core` | заголовок кадра + CRC32, фрагментатор, сборщик, запись/чтение `.mlrec` | ✅ собрано, проверено |
| `MouthLink.Emulator` | эмулятор источника: шлёт синтетические кадры вместо шлема | ✅ |
| `MouthLink.Receiver` | приём, сборка, статистика, запись сессии, живой просмотр в браузере | ✅ |
| `MouthLink.Player` | офлайн-плеер `.mlrec`: пауза/шаг/перемотка/скорость | ✅ |
| `training/` | обучение модели (PyTorch): датасет, CNN, аугментации, экспорт ONNX | ✅ прогнано на синтетике |
| `tools/mlrec2png.py` | разложить запись в PNG | ✅ |
| `tools/mlrec_check.py` | проверка записи: частота, пропуски, плохие/застывшие кадры, тестовый шаблон | ✅ |

Эмулятор позволяет поднять и отладить всю сторону ПК **без шлема** — он шлёт кадры
в том же формате, что будет слать шлем.

## Как запустить сегодня (без шлема)

**1. Поток и просмотр.** Два терминала.

Эмулятор (источник на :9040, кадр 320×240, 60 fps):
```
dotnet run --project MouthLink.Emulator -- 9040 320 240 60
```
Приёмник (подписка, просмотр, запись):
```
dotnet run --project MouthLink.Receiver -- --host 127.0.0.1 --ctrl 9040 --listen 9041 --fps 60 --view 8080 --record session.mlrec
```
Открой `http://localhost:8080/` — там идёт синтетический «рот». Приёмник раз в
секунду печатает fps, потери, Мбит/с и задержку. Просмотр слушает только loopback.

**Проверка передачи изображения.** Эмулятор с `--pattern` шлёт детерминированный
тестовый шаблон, приёмник с `--verify` сверяет каждый кадр попиксельно и пишет
`сверка: N/N ок` в строке статистики (там же `пропуск_id` — потерянные номера кадров):
```
dotnet run --project MouthLink.Emulator -- 9040 400 400 90 --pattern
dotnet run --project MouthLink.Receiver -- --host 127.0.0.1 --verify --record pattern.mlrec
```
Проверка готовой записи (частота, ровность, пропуски, чёрные/пересвеченные/застывшие
кадры, обрезанный хвост; с `--pattern` — попиксельно):
```
python tools/mlrec_check.py pattern.mlrec --pattern
python tools/mlrec_check.py session.mlrec --csv frames.csv
```
Когда появится реальный поток: сначала пусть источник шлёт шаблон (`--verify` должен
показать всё ок), потом — настоящие кадры, и `mlrec_check.py` без `--pattern` покажет,
здоров ли поток камеры.

**2. Плеер записи.** Проиграть `session.mlrec` офлайн:
```
dotnet run --project MouthLink.Player -- session.mlrec 8081
```
`http://localhost:8081/` — пробел играть/пауза, ←/→ шаг, плюс перемотка и скорость.

**3. Обучение модели.** Проверка всего конвейера на синтетике (нужен Python +
PyTorch):
```
cd training
python make_synth_dataset.py --out data/synth --n 3000 --sessions 10
python train.py --data data/synth --out runs/synth --epochs 20
python export_onnx.py --ckpt runs/synth/best.pt --out runs/synth/mouth.onnx
python infer_demo.py --onnx runs/synth/mouth.onnx --data data/synth --n 8
```
Обучение делит train/val **по сессиям** (разная посадка шлема), с сильными
аугментациями и опционально предобученным MobileNetV3 (`--arch mnv3 --pretrained`).
`--cv` исключает каждую сессию по очереди. Детали и результаты — `training/README.md`.

Сборка C#: нужен .NET 8 SDK, `dotnet build` в корне решения.

## Граница

Захват кадров **изнутри сервиса шлема** (инжект в `pxreyetrackingservice`, чтение
буферов камеры) в этот репозиторий не входит и пишется на стороне шлема —
самостоятельно или вместе с автором PicoET (там это уже в планах, и глаза с ртом
живут в одном процессе, так что один захват логичнее двух инжектов).

MouthLink начинается там, где кадр уже готов к отправке. Чтобы твой код захвата
стал источником для готового приёмника, он должен:

1. слушать UDP 9040, по `SUBSCRIBE` взять адрес ответа и желаемый fps;
2. на каждый кадр заполнить 42-байтовую шапку `FrameHeader`, порезать на куски
   ≤1400 байт, посчитать CRC32 по первым 38 байтам, отправить;
3. отвечать на `PING`→`PONG` и `DISCOVER`→`HELLO`.

Это ровно то, что делает `MouthLink.Emulator` — он и есть референс источника,
только рисует кадр синтетически вместо чтения камеры. Полные байтовые раскладки —
в `PROTOCOL.md`.

## План модели

1. **Дистилляция стока.** Пишем запись кадров + стоковые блендшейпы из бриджа,
   спариваем по времени, учим маленькую сеть повторять сток. Рабочий бэкбон на
   проверенных данных.
2. **Персональная калибровка.** Короткая сессия с подсказками выражений
   (рампа 0→1→0): «улыбка слева», «надуть правую щёку», «язык влево». Правит формы,
   где сток врёт, и добавляет каналы, которых у стока нет. Поддержано частичным
   лейблом: подсказка размечает только свой канал.
3. **Инференс на ПК** (ONNX Runtime из C#) → модуль VRCFT → рот в VRChat.

## Приватность

Кадры камеры рта — снимки лица. Записи `.mlrec`, выгрузки PNG, датасеты и веса,
обученные на лице, остаются только локально: `.gitignore` с первого коммита
закрывает `data/`, `runs/`, `*.mlrec`, `*.raw`, `*.npy`, `*.onnx`, `*.pt`. В
репозиторий попадает только код. Просмотр и плеер слушают только loopback.
